# Receipt Protocol v2.8

## Abstract

A receipt is a verifiable, signed claim that an agent performed an action on a platform at a point in time. Receipts are designed to be portable across venues — they travel with the agent, not the platform.

This is **self-attested** proof. It proves "the agent claims this happened," not "this actually happened."

---

## Receipt Format

```json
{
  "schema_version": "2.8",
  "id": "uuid-v4",
  "agent_id": "string",
  "agent_pubkey": "base64 Ed25519 public key | null",
  "agent_signature": "base64 Ed25519 signature | null",
  "action": "string",
  "platform": "string",
  "outcome": "success | failure | pending",
  "proof": "string | null",
  "related_receipts": [
    {
      "id": "string",
      "digest": "string | null",
      "relationship": "admission | outcome | previous | other"
    }
  ],
  "prev_receipt_hash": "string | null",
  "trust_level": "self_attested | third_party_attested | anchored",
  "issued_at": "ISO-8601",
  "server_signature": "base64 Ed25519 signature",
  "server_pubkey": "base64 Ed25519 public key"
}
```

### Fields

| Field | Type | Required | Description |
|---|---|---|---|
| schema_version | string | yes | Schema version, currently "2.8" |
| id | string | auto | UUID v4, generated by server |
| agent_id | string | yes | The agent who performed the action |
| agent_pubkey | string | no | Agent's public key (if the agent signed the payload) |
| agent_signature | string | no | Agent's signature over the canonical JSON payload |
| action | string | yes | What the agent did |
| platform | string | yes | Where the agent did it |
| outcome | string | yes | success / failure / pending |
| proof | string | no | Optional link/hash for verification |
| related_receipts | array | no | Optional list of related receipts, each with id, digest, and relationship type |
| prev_receipt_hash | string | no | Optional hash of the previous receipt in a chain |
| trust_level | string | yes | How much you should trust this receipt |
| issued_at | string | auto | ISO-8601 timestamp |
| server_signature | string | auto | Server's Ed25519 signature over canonical JSON |
| server_pubkey | string | auto | Server's public key |

## Related Receipts

Receipts can be linked to other receipts about the same action. This is optional — individual receipts are still the default.

Each entry in `related_receipts` has:
- **id** — the ID of the related receipt
- **digest** — optional content digest, to bind the link to the actual content
- **relationship** — what kind of relationship this is:
  - `admission` — this receipt links to the admission decision that authorized the action
  - `outcome` — this receipt links to the observed outcome from the target system
  - `previous` — this receipt links to the previous step in a workflow
  - `other` — any other relationship

### Why we use a typed list instead of just parent_receipt_id

Different receipts answer different questions:
- Admission receipt — "was this allowed?"
- Execution receipt — "the agent claims it did this"
- Outcome receipt — "the target says this happened"

They all refer to the same action, but from different perspectives. A typed list lets you link to all of them without special-casing.

## Signatures

A receipt can have up to two signatures:

### Agent signature (optional)
- The agent signs the receipt payload themselves
- Proves "the agent made this claim"
- If present, `agent_pubkey` and `agent_signature` are both required

### Server signature (always present)
- The server signs the receipt
- Proves "the server recorded this claim"
- This is always present — it's how we know the receipt came from our registry

---

## Receipt Chains (optional)

Receipts can optionally be chained together. This is off by default.

When chaining is used:
- Each receipt has a `prev_receipt_hash` field
- This field contains the SHA-256 hash of the previous receipt in the chain
- Chaining proves order and completeness

## Trust Levels

| Level | What it proves |
|---|---|
| `self_attested` | The agent claims it did something, the server signed it |
| `third_party_attested` | A third party verified the claim |
| `anchored` | The receipt hash is anchored to a public ledger |

---

## Semantics

### What a receipt proves
- An agent claims to have done something
- The signature is valid
- The receipt hasn't been tampered with
- If linked, it relates to other receipts about the same action

### What a receipt does NOT prove
- That the agent is who they say they are
- That the action actually happened
- That the linked receipts all agree with each other

---

## Design Decisions

1. **No auth** — friction is the enemy of adoption
2. **Self-attested by default** — minimal layer, add trust on top
3. **Portable** — receipts travel with the agent
4. **Offline verification** — no server call needed
5. **Versioned schema** — semver
6. **Optional complexity** — chaining, dual signing, linked receipts are all optional
7. **Typed relationships** — linked receipts have explicit relationship types
