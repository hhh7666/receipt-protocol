# Receipt Protocol v2.7

## Abstract

A receipt is a verifiable, signed claim that an agent performed an action on a platform at a point in time. Receipts are designed to be portable across venues — they travel with the agent, not the platform.

This is **self-attested** proof. It proves "the agent claims this happened," not "this actually happened."

---

## Receipt Format

```json
{
  "schema_version": "2.7",
  "id": "uuid-v4",
  "agent_id": "string",
  "agent_pubkey": "base64 Ed25519 public key | null",
  "agent_signature": "base64 Ed25519 signature | null",
  "action": "string",
  "platform": "string",
  "outcome": "success | failure | pending",
  "proof": "string | null",
  "parent_receipt_id": "string | null",
  "parent_receipt_digest": "string | null",
  "prev_receipt_hash": "string | null",
  "trust_level": "self_attested | third_party_attested | anchored",
  "issued_at": "ISO-8601",
  "server_signature": "base64 Ed25519 signature",
  "server_pubkey": "base64 Ed25519 public key"
}
```

### Fields

| Field | Type | Required | Description |
|---|---|---|---|
| schema_version | string | yes | Schema version, currently "2.7" |
| id | string | auto | UUID v4, generated by server |
| agent_id | string | yes | The agent who performed the action |
| agent_pubkey | string | no | Agent's public key (if the agent signed the payload) |
| agent_signature | string | no | Agent's signature over the canonical JSON payload |
| action | string | yes | What the agent did |
| platform | string | yes | Where the agent did it |
| outcome | string | yes | success / failure / pending |
| proof | string | no | Optional link/hash for verification |
| parent_receipt_id | string | no | Optional ID of a parent receipt (e.g. an admission receipt) |
| parent_receipt_digest | string | no | Optional content digest of the parent receipt |
| prev_receipt_hash | string | no | Optional hash of the previous receipt in a chain |
| trust_level | string | yes | How much you should trust this receipt: self_attested / third_party_attested / anchored |
| issued_at | string | auto | ISO-8601 timestamp |
| server_signature | string | auto | Server's Ed25519 signature over canonical JSON |
| server_pubkey | string | auto | Server's public key |

## Signatures

A receipt can have up to two signatures:

### Agent signature (optional)
- The agent signs the receipt payload themselves
- Proves "the agent made this claim"
- If present, `agent_pubkey` and `agent_signature` are both required

### Server signature (always present)
- The server signs the receipt
- Proves "the server recorded this claim"
- This is always present — it's how we know the receipt came from our registry

### Verification

To verify a receipt:
1. Verify the server signature (always)
2. If agent signature is present, verify that too
3. Check that the agent's pubkey matches the agent_id (if you have an identity registry)

## Receipt Chains (optional)

Receipts can optionally be chained together. This is off by default — individual receipts are still the simplest and most common use case.

When chaining is used:
- Each receipt has a `prev_receipt_hash` field
- This field contains the SHA-256 hash of the previous receipt in the chain
- Chaining proves two things:
  1. **Order** — receipts cannot be reordered after the fact
  2. **Completeness** — a receipt cannot be removed from the middle of the chain

### When to use chaining

Use chaining when:
- You have a sequence of actions that need to be proven in order
- You want to make backdating harder
- You're building an audit log

Don't use chaining when:
- You just need to prove a single action happened
- Simplicity is more important than integrity guarantees

## Trust Levels

Receipts come with different trust levels. The receiver should decide how much weight to give each level:

### `self_attested` (default)
- The agent claims it did something
- The server signed that claim
- The signature is valid (cryptographic fact)
- The receipt hasn't been tampered with

This is the minimum bar. It proves "this key signed this claim," not "this claim is true."

### `third_party_attested`
- A third party (not the agent, not the registry) has verified the claim
- This could be a witness, an auditor, or another agent

### `anchored`
- The receipt hash has been anchored to a public ledger (e.g. a transparency log)
- This makes backdating harder — you can't fake months of history overnight

---

## Semantics

### What a receipt proves

- An agent claims to have done something
- The server signed that claim with Ed25519
- The signature is valid (cryptographic fact)
- The receipt hasn't been tampered with
- The trust level tells you how much external verification there is
- If chained, the order and completeness of the sequence
- If agent-signed, the agent themselves made the claim

### What a receipt does NOT prove

- That the agent is who they say they are (identity verification)
- That the action actually happened (observed outcome)
- That the proof is genuine

These require peer attestation, external verification, or admission receipts from a verifier.

## Design Decisions

1. **No auth** — friction is the enemy of adoption. Start open, add auth later if needed.
2. **Self-attested by default** — we start at the minimal layer. Anyone can add trust on top.
3. **Portable** — receipts travel with the agent, not the platform.
4. **Offline verification** — you don't need to call us to verify a receipt.
5. **Versioned schema** — we follow semver. Breaking changes bump the major version.
6. **Optional chaining** — we don't force everyone to use chains. Use them if you need them.
7. **Dual signing** — agent can sign the claim, server signs the recording. Both are optional and complementary.
